## 1. Purpose and scope

Specify a Linux-native debugger architecture that can be implemented and tested **entirely offline** in the next stage. D48 freezes the proposed *module boundaries, interfaces, evidence classification, and safety requirements*; it does **not** certify the proprietary cable protocol or authorize communication with hardware.

The D48 documentation authorization covers only these two Markdown files. It does not authorize creation of implementation modules, modifications to the existing compiler, use of the physical serial port, target reset, or flash operations.

## 2. Baseline and repository integration

The repository currently contains `ez8native/` (assembler, linker, firmware and related modules), `tests/`, `docs/hardware/`, and an untracked `tools/` directory. The last observed Git state was `?? tools/`; that directory must remain untouched. `docs/hardware/` contained no tracked files at the D48.4 review. The proposed `ez8native/debugger/` namespace was absent and available.

Do not alter the G2.4 baseline modules or their public CLI behavior. Debugger implementation, when separately authorized in D49, is a new subpackage under `ez8native/debugger/` with tests under `tests/`.

## 3. Logical architecture and dependency rules

```text
CLI / offline diagnostics
         |
Z8 OCD abstraction (target operations; unimplemented/blocked)
         |
Smart Cable protocol (encoding, validation, state machine)
         |
Transport abstraction (no OS-specific dependency)
         |
Mock transport (only permitted V0.1 backend)

Physical serial transport: BLOCKED / no enabled implementation in V0.1
```

Dependencies must flow downward. Neither the OCD nor the protocol layer may import `serial`, open device nodes, or invoke Windows APIs. The transport abstraction must not interpret Z8 OCD opcodes. A CLI check alone is insufficient for safety: session and transport boundaries must also reject forbidden operations.

### 3.2 Interface contracts (design, not executable API)

| Interface | Contract |
|---|---|
| `write_all(data: bytes)` | Complete write in Mock or explicit failure; no partial success silently accepted. |
| `read_exact(length: int) -> bytes` | Exactly requested length or explicit short-read/timeout failure. Validate length bounds. |
| `set_baud(rate: int)` | Mock-only state transition and audit log; no physical I/O. |
| `close()` | Idempotent; no target action. |
| `encode_identify()` | Return candidate request `80` with evidence label `STATIC_DLL`. |
| `parse_identify(data)` | Require six bytes and compare bytes 3–5 to `55 88 11`; bytes 0–2 remain uninterpreted. |
| `encode_baud(57600)` | Return candidate `00 00 14`, **offline only**; do not generalize unverified rates. |
| `connect()` | Mock session only; reject physical transports before any port-open side effect. |
| OCD methods | Explicitly unavailable for hardware; mocks may return labeled synthetic fixtures. |

Error categories should distinguish unsupported operation, protocol validation failure, timeout/short read, and safety-policy violation. Mock fixtures must be labeled synthetic and never represented as captured device responses.

## 4. Session state machine

Proposed offline states: `DISCONNECTED`, `MOCK_OPEN`, `IDENTIFIED_MOCK`, `BAUD_CONFIGURED_MOCK`, `CLOSED`, `ERROR`.

The static DLL analysis identifies a conditional branch in which a cable-identification check is followed by COM timeout configuration, cable-side baud command, a 300 ms delay, then host-side DCB baud configuration. The branch taken when identification fails is not yet fully analyzed. The mock state machine may model the **known branch** as a fixture; it must not imply the branch is universal or hardware-verified. It must never sleep merely to mimic the DLL unless a test explicitly needs a virtual clock.

## 5. Safety contract — fail closed

1. V0.1 permits **only Mock Transport**. A physical serial backend is not enabled.
2. Never open `/dev/ttyUSB0` or any other device, even for a supposedly read-only debugger operation.
3. Never send a cable command to hardware or change real DTR/RTS/CTS, baud, or line settings.
4. Block all target reset, flash unlock, page erase, mass erase, programming, and unverified OCD commands.
5. Do not treat device-ID reads or debugger attach as inherently non-mutating: the legacy target algorithm includes reset and flash-control operations.
6. Unknown commands, invalid responses, unexpected state transitions, or unsupported baud values must fail closed.
7. Require enforcement at both the session and transport boundaries; do not rely solely on CLI validation.
8. No automated test may require a connected MCU, smart cable, FTDI adapter, Wine, or Windows DLL.
9. Preserve existing `tools/`, G2.4 files, and source DLLs; D48 itself creates documentation only.
10. Hardware communication and flash programming remain separately gated and unauthorized.

## 6. Evidence and confidence policy

Use the following labels consistently:

- `HOST_OBSERVED`: host-side enumeration or repository state directly observed.
- `STATIC_DLL`: bytes, control flow, or API use established by disassembly; **not** observed on a wire.
- `CONFIGURED`: value present in configuration; runtime propagation not necessarily established.
- `INFERRED`: interpretation or proposed semantic meaning supported but not proved by source.
- `UNVERIFIED`: no direct supporting observation.
- `HARDWARE_VERIFIED`: reserved for future explicitly authorized, documented hardware tests; **none currently**.

Do not convert `STATIC_DLL` or `CONFIGURED` evidence into `HARDWARE_VERIFIED` claims. See the companion protocol evidence document.

## 7. Testing and acceptance criteria

The repository mixes `unittest` and `pytest`; `make test` invokes `unittest discover` and is not a complete pytest regression. The static count of 76 top-level `def test_` functions is not a collected-test total. The prior G2.4 reported baseline of 118 tests and 24 subtests is historical, not re-executed during D48.

D49 implementation acceptance (not performed in D48):

- Mock transport exercises exact write/read semantics and errors.
- Protocol tests cover candidate `80`, `00 00 14`, malformed identification responses, and unsupported baud rates.
- State-machine tests cover known conditional path, failures, and forbidden transitions.
- Safety tests prove that device opens and target-mutating operations cannot be reached, including by direct module imports.
- Existing G2.4 regression is run separately without modifying the baseline.
- A new code change requires its own review and explicit authorization.
